## 0. 结论（先看这里）

1. Duplex 的核心思想有三条，**对我们都能借鉴，但都不能照搬**：
   - **按时间切片，而不是按回合**：每 160 ms 一个 chunk，输入输出同步推进，**沉默也是 chunk**；模型每一步自己决定“说 / 不说 / 嗯一声 / 让出”，并能识别“这句话不是对我说的”。
   - **边听边想、边想边答**：理由随着短语到来持续增长，不等整个问题；工具调用尽早异步发出，用**部分结果**就开始回答。
   - **前台模型 + 后台大模型委派**：前台先答，复杂的交给大模型并**共享完整上下文**，对话不中断，结果回来再补。
2. **上下文管理**它做了一个我们很能用的选择：**会话是有状态的**（只喂新 chunk，不重发历史），保留“最近 5 分钟的原始流 + 压缩后的文字”，更早的以文字保留；设计目标是**一小时成本 ≤ 人工一小时的 1/10**，所以每个流都被“挤”到最小。我们是无状态 API，靠“只增不改的前缀 + 服务商缓存”模拟了有状态——这一点**我们的方向与它一致**，缺的是**测量与成本意识**（目前根本不知道缓存是否命中、每小时多少 token）。
3. **最值得做的 4 件事**（按性价比）：
   ① **先测量**（T-204/T-101，已在计划里）；② **流式预热**：对方说话过程中就把整场对话前缀打进缓存，说完时只需补几个 token（成本很低，对应 Duplex 的“边听边想”）；③ **双层应答**：先给一句可以直接说出口的开场，再异步给详细版（对应“前台 + 后台委派”）；④ **说完立刻显示“检测到的问题”**，不等 LLM（对应“嗯”这类即时确认，几乎零成本就能显著改善体感延迟）。
4. **不该学的**：45B 全双工端到端模型、音频 token 化、人脸渲染、用 RL 训练“何时说话”——要么做不到，要么和 Copilot 的形态不符（我们的输出是给人看的屏幕文字，不是要“抢话”）。
5. **现状 check 的关键发现**（§1）：自 v0.1.1 以来 DSH 合并了大量 UI/ASR/历史功能（v0.1.2–v0.1.6），**触发与上下文的核心逻辑一行没动**；我之前指出的缺陷在 `main` 上**全部还在**（自动触发打断回答、截图在关键路径、无遥测、ISS-014）。

## 2. Higgs Realtime Duplex 是怎么做的（只含资料里写的）

### 2.1 时间切片，不是回合
- 所有流（你的声音、摄像头、工具结果、后台回复；它的声音、脸、思考）切成 **160 ms 的 chunk**。每一步“读刚到的 chunk，写下一个要播放的 chunk”，**沉默区间也用 chunk 表示**，开着视频时画面在沉默期间也持续输入——“模型从不停止听和看”。
- 它**自己决定何时说话**：说“嗯哼”、抢在你说完之前回答、你插话时停下、忽略背景噪声和**不是对它说的话**（博客的例子：免下车点餐时它保持安静，等你点完才汇报；它“听到了每个字，也知道哪些是对它说的”）。
- 人类的参照：对话中回应通常落在对方说完后 **200 ms** 内，有时在对方说完之前（时机合适时）。

### 2.2 边听边想，用部分结果答
- 思考“通常要几秒，没人想每次都等几秒”：每出现一个有意义的短语或想法，模型就在**一条持续的推理线程**上接着想，**不等完整问题**；推理跨 chunk 进行，边说边想。
- 工具调用“尽可能早地、异步地”发出，**用部分结果就开始回答**；有的工具分阶段返回中间结果，模型不等完整结果。

### 2.3 前台模型 + 后台委派
- 前台模型（45B MoE）直接对话，自己思考、调工具；任务超出能力时**连同完整共享上下文**交给更大的后台模型，同时继续对话（甚至聊别的），结果好了再带回来。
- 与 Thinking Machines 的方案不同：对方把思考和工具调用都交给后台模型（训练简单，但大推理模型可能要 10 秒以上才响应，且每轮都调用成本难控）；Duplex 让前台自己处理大部分请求，**只在必要的轮次才用后台**。

### 2.3′ 令牌预算与上下文
- 全双工下模型**每个 chunk 都在处理，哪怕没人说话**，上下文增长很快，所以“把每个流都挤到最小”：音频输入 6.25 token/s、输出 12.5 token/s、摄像头每 6 个 chunk 一帧（约十几个 token）、人脸 2 个 latent/chunk。
- 音视频约 **2.6K token/分钟**；加上可选的思考和工具调用约 **2.6–5K token/分钟**，这个估计已经**假设了对中间推理和工具痕迹的渐进式压缩**（保留继续工作所需的信息）。
- 生产中通常保留**最近 5 分钟的音频/视频流 + 压缩文本**（约 13K–25K token），**更早的历史以文字形式另外保留**。
- 设计目标：**一小时的成本 ≤ 人工一小时成本的 1/10**。

### 2.4 训练（决定“何时说话”的来源）
- **多教师在线蒸馏（MOPD）**：从同一个基座出发，用强化学习（含 GRPO）在几组相关任务上训练专家教师——自然对话、交互行为、动态委派、任务完成；教师在交互中学会“说什么、何时行动”（何时说话或让出、开始或延长一条推理线程、调工具、委派），再蒸馏成一个学生。
- **递归自我改进（RSI）**：agent 系统与仿真环境交互 → 复盘失败 → 合成针对性数据 → 训练 → 重复。仿真必须**复现真实交互的时序和多样性——打断、重叠说话、旁路对话、背景噪声**；“工程目标是整个 harness（仿真器、工具、评审），而不是孤立的模型”。

### 2.5 上一代 Higgs Realtime（API 已可用）与官方 API 文档
- 声称**语义 turn detection 帮助模型区分“说完了”和“只是停顿”**；说完后约 **0.70 s** 出第一个音频帧，被打断后 **0.125 s** 停止说话。
- 与 OpenAI Realtime API 兼容。API 文档里 `turn_detection.type` 可为 `server_vad` 或 `semantic_vad`；`server_vad` 默认值（文档示例）：`threshold 0.85`、`prefix_padding_ms 300`、**`silence_duration_ms 500`**、`min_speech_duration 0.125`。`turn_detection: null` 是**手动模式**：`input_audio_buffer.commit` 提交为一个用户回合，**commit 本身不会生成回复**，需要再发 `response.create`。输入转写可启用 `higgs-stt-3.1`。
- 计费（博客）：输入 token $0.75/百万，**缓存的输入 token $0.25/百万（约 1/3）**，输出 $4.50/百万；音频输入 $0.0023/分钟。

## 4. 可借鉴的点（按价值排序）

> 每项：借鉴什么 → 对应的计划编号 → 做法 → 验证 → 风险。**除 L5/L4 外都应在 T-204（遥测）之后做。**

### L2　边听边“预填”：流式预热 + 推测生成（P5/P6 的具体化）　**价值最高 / 成本可控**
- **借鉴**：Duplex 不等完整问题——短语一到就接着想。我们对应的是：**对方说话期间，就把“整场对话 + 已识别的这一轮前半句”这个前缀提前打进服务商缓存**，等触发时只需补末尾几个 token，首字延迟被压低。
- **做法（分三级，逐级加码，每级默认关闭）**：
  1. **预热（最便宜）**：监听开始/每个新轮开始时，发一个 `max_tokens=1` 的极短请求，把整场对话前缀（含会议背景）写进缓存；之后在对话里每隔几句、或对方每出现一个“短语边界”，再预热一次（前缀只增不改，所以每次只多算新增部分）。**只花输入 token，且大部分已缓存**。
  2. **边听边预填**：在对方这一轮进行中，用最新的临时结果更新“当前这一轮”并再预填；说完时请求只差最后几个 token。
  3. **推测生成**：判断“大概率说完”（句末问号等）时就**隐藏地**发起完整请求，静音确认后再揭示（= P6）。
- **验证**：必须靠 T-101 的“缓存命中率 / 首字耗时”看是否真的有收益（**不同服务商缓存规则不同**：Higgs 公开价是缓存输入约为普通输入的 1/3，我们所用服务商的价差需要实测）。
- **风险**：预热会增加请求数和费用（每次仍计未缓存的新增部分）；把预热请求误展示给用户；与 P2 的“隐藏直到确认”机制耦合。

### L3　双层应答：前台快速开场 + 后台详细版（对应“前台模型 + 委派”）　**新增 P11 / T-216**
- **借鉴**：前台先答，后台大模型在共享上下文上做深度思考，结果回来再补，对话不停。
- **做法**：触发后并行两个请求——**快模型（或同一模型限制 `max_tokens≈120`、提示“只给可以直接说出口的开场 + 一句结论”）**立刻显示；**主模型**生成详细版，到达后**追加/替换**（保留已显示的开场，不闪烁）。设置里可配两个模型槽（默认只有一个＝现在的行为）。
- **价值**：面试里“先有话说”比“答案完美”更重要；也自然缓解“主模型首字慢”的问题（现在 E2E 首字延迟未知）。
- **风险**：成本 +1 次调用（短）；两段内容的一致性；UI 的“追加”表现（与 T-302 衔接）。
- **验证**：回答质量基线（T-105）对比“仅详细版”与“开场 + 详细版”的评分；E2E 首字时间。

### L4　说完立刻显示“检测到的问题”（对应“嗯哼”式即时确认）　**几乎零成本**
- **借鉴**：不等答案就先给出反馈。
- **做法**：触发那一刻（甚至更早，句末问号定稿时）就在答案区显示“**检测到：<这一轮对方的问题原文>**”和“生成中…”状态；若判定“无需回答”则静默撤掉。这也是 U2/U3 的核心。
- **价值**：把“感觉没反应”的几秒变成“系统听到了、在处理”；同时让用户立刻能核对“识别到的是不是这一问”。
- **依赖**：T-301/T-302（UI 拆分与状态条）；逻辑上不依赖任何模型改动。

### L1　tick 式端点判定：连续评估代替一次性定时器　**中等价值 / 先做等价重构**
- **借鉴**：Duplex 每个 chunk 都在决策，沉默是输入；我们的 `TurnDetector` 是“定稿时算一个 wait → `Task.sleep` → 到点检查”，之后的每种新信息只能“整体取消”。
- **做法**：把判定改成**每 100–160 ms（或每个事件）评估一个“应当现在回答”的分数**：输入 = 已静音多久、句末类型、是否像问题、临时结果稳定度、对方/我的语音起止信号、回声……；分数连续 ≥ 阈值 k 个 tick（滞回）才触发。**第一步只做行为完全等价的重构**（用 `EquivalenceTests` 和评测证明不变），第二步才引入可调权重，使“灵敏度”变成**一个连续旋钮**（类似 OpenAI Realtime `semantic_vad` 的 eagerness 概念——*Higgs 文档里没查到该参数，未核实*）。
- **价值**：为 P5（推测定稿）和 L2 的“大概率说完时预发请求”提供自然的挂载点；让评测能扫描阈值曲线（时机 vs 抢答的 Pareto），而不是现在的三档。
- **风险**：重构面大（`TurnDetector.swift` 热文件）；收益要靠评测 v2 才能看清（T-201）。

### L5　令牌预算与成本意识　**依赖 T-101；与“上下文先全部给模型”不冲突**
- **借鉴**：Duplex 把“一小时成本 ≤ 人工 1/10”作为设计目标，并按 token 精算每个流。
- **做法**：T-101 之上加**成本面板**：每次请求的输入/缓存命中/输出 token、估算费用、**每小时累计**；超预算提示。顺手：**把此前的 AI 回答（“此前建议”）在较早的轮次压缩成一两句要点**（对应它“渐进压缩中间推理/工具痕迹”），整场对话文字**不压缩**（沿用“全部交给模型”，并吸取 v0.1.0 滚动摘要有损的教训）。
- **验证**：有成本数据后，才谈 T-102（按 token 的上限）。

### L6　“不是对我说的”：点名与说话人（多人会议）
- **借鉴**：Duplex 能识别旁路对话、不是对它说的话。我们现在只有“确认/寒暄/过渡语”。
- **做法**：近期低成本版——**点名线索**：从“会议背景”里提取我的称呼（姓名/角色），对方这一轮里出现“请 X…”且 X 不是我 → 不触发；出现我的称呼 → 优先触发。远期——说话人区分（T-050）。
- **风险**：中文姓名/称呼的歧义；只对多人会议有意义，面试 1v1 基本不需要，所以**不是近期重点**。

### L7　仿真驱动的评测扩展（对应 RSI 的“仿真要复现真实交互”）
- **借鉴**：仿真应包含**打断、重叠说话、旁路对话、背景噪声**；失败 → 合成针对性数据 → 再评估；“harness 才是工程目标”。
- **做法**：评测 v2（T-201）与留出集（T-202）里**新增这四类场景**；并研究 **Full-Duplex-Bench / ProactiveVideoQA（PAUC）** 的度量——博客只给了名字和分数，**具体定义需要查原论文，本次未查**。把我们现在“抢答/漏答/误答”的二值判定，补成**连续的时机得分**（回答时刻相对真实说完时刻的偏差惩罚）。
- **注意**：这个循环正是我们自己做过的（人工写数据、改规则），已经观察到**过拟合风险**——所以数据要由 DSH 独立盲写（T-202）。

### L8　打断语义：对方改口/插话时旧答案失效
- **借鉴**：用户插话它 0.125 s 内停下并**重新规划**。
- **做法**：并入 P2（`AnswerScheduler`）：对方改口/追加新问题时，旧答案标为“已过期”并折叠；新一轮的答案不截断仍在生成的旧答案（除非是同一轮的延伸）。

### L9　静音阈值参照（谨慎）
- Higgs 的 `server_vad` 示例默认 **500 ms**，我们是 **800 ms**。这是**P5 的实验起点而不是结论**：实时语音助手需要抢话，所以更激进；我们的场景是“别抢答对方”，且 800 ms 之外还有规则等待。**先用 T-204 的数据看真实停顿分布，再用评测 v2 对比 500/650/800 ms，不要直接改。**

### L10　（可选，需用户同意）云端模式：把实时 API 的语义断句当作触发源
- Higgs Realtime 的 API 与 OpenAI Realtime 兼容，支持 `semantic_vad` 与“手动模式（不自动生成回复）”，输入音频约 $0.0023/分钟。理论上可以在**云端模式**下，把系统音频流给这个 API，**只用它的“语义断句”事件和转写**，再由我们自己的 LLM 生成答案——与 DSH 已加的云端 ASR 思路一致。
- **但**：①音频上云违背“本地优先”的默认（只能是可选并明确提示）；②我**没有验证**它是否对外暴露“语义断句”的事件、延迟多少、中文表现如何；③依赖第三方服务稳定性。**建议只作为后续调研项，不进入近期计划。**

## 5. 不该学的 / 不适用

- **端到端全双工模型**（45B MoE、2T token 训练、H100 集群、RL 学“何时说话”）：我们没有这种数据和算力；且 API 尚未开放，**它“何时说话”的决策也无法作为独立信号取出**。
- **音频 token 化与有状态会话**：我们用的是通用文本 LLM API（无状态）；能做的是“只增不改的前缀 + 缓存”，已经在做。
- **“保留最近 5 分钟原始流、更早压缩”**：它压缩的是音频/视频流和推理痕迹；我们整场对话本来就是文字，**目前不压缩**（你要求先全部交给模型；v0.1.0 的滚动摘要有损、已被淘汰）。只有把旧 AI 回答压缩（L5）这一小块可借鉴。
- **让 AI 抢话**：Duplex 的“在你说完前回答”是语音助手的价值；Copilot 是给人看的屏幕文字，**宁可晚 1 秒也不能在对方没说完时给出残缺答案**（这也是我们把“抢答”当主要缺陷的原因）。
