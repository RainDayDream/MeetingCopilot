# 模型调用时机（触发）：分析与实现方案规划

- 状态：**规划，待用户审核后分配任务**（本文没有改任何代码）
- 作者：Claude　日期：2026-10-21　基线：`main` @ `a6537a3`（v0.1.1）
- 范围：只讨论“**什么时候调用模型**”（自动触发、手动触发、触发后的请求与展示的时序）。**上下文暂时维持现状：把整场对话全部交给模型**，不在本文范围。
- 约定：**[实测]** = 我在本机跑出来的数；**[评测]** = 冻结/扩展评测里的数（合成数据 + 假设的时序模型）；**[假设]** = 没有数据支撑的估计，必须先测。

## 0. 结论（先看这里）

1. **触发的“判断”已经基本够用，真正的瓶颈在“判断之后”和“判断之前”：**
   - **判断之前（识别流水线）**：定稿延迟固定 0.8 s（VAD）+ 识别 0.26–0.55 s [实测]。评测里假设的 0.7 s 偏保守，真实的“说完→可触发”下限大约 **1.2–1.35 s，而不是 1.55 s** [实测推算]。
   - **判断之后（请求链路）**：截图在关键路径上、LLM 首字延迟、网络建连——这些**目前完全没有测量**，很可能比 1.5 s 的触发延迟更大。
2. **有 2 个会直接伤害体验的缺陷，应该最先修**（不依赖任何数据）：
   - **自动触发会打断上一条正在生成的回答**（`AppModel.swift:243`）——哪怕新触发最后判定为“（无需回答）”，上一条也已经被截断。
   - **识别引擎是串行的，partial 与 final 抢同一个队列**；final 最多被前面一个 partial 多挡 ~0.5 s，长会议/大模型/慢机器上会累积 [实测：两个 12 s 请求并发 = 0.92 s，两者是排队的]。
3. **没有端到端的测量**：现在没人能回答“对方说完到我看到第一个字用了多久、慢在哪一段”。所以**第一步必须是做时序遥测（P1）**，之后所有延迟优化（P4–P6）都用它的数据决定做不做、做多少。
4. 一共拆成 **10 个问题（P1–P10）**，按“先测量 → 先修正确性 → 再压延迟 → 最后提质量”排序，每个问题都是独立的小任务，有推荐方案、备选方案、验收和风险。
5. 延迟方案里**收益最大也最复杂的是“推测式”**（P5 推测定稿、P6 推测式请求）；它们依赖 P1 的数据和 P2 的“隐藏直到确认”机制，所以放在后面，**且都做成默认关闭的设置开关**。

## 1. 目标与度量

**用户视角的目标**：对方问完后，尽快在屏幕上看到针对**这一问**的答案开头；不该答的时候不打扰、不打断；我自己在说话时不被干扰。

| 指标 | 定义 | 现状 |
|---|---|---|
| **T_trigger** | 对方说完 → 触发决定 | 评测 1.55 s [评测]；实测推算 ≈ 1.2–1.35 s [实测推算] |
| **E2E_first_token**（最重要，**目前无数据**） | 对方说完 → 答案第一个字显示出来 | **未测量** |
| 抢答率 / 漏答率 / 误答率 / 重复触发 | 冻结评测口径 | 21.7% / 0 / 25.0% / 17；扩展 0.0% / 0 / 10.0% / 0 |
| **被打断的回答数** | 一条回答在生成中被新的触发取消 | 未统计；代码上每次自动触发都会取消上一条 |
| **ASR final 排队时间** | final 请求提交 → 开始识别 | 未测量 |
| 推测浪费率（P5/P6 之后） | 被取消的推测请求 / 全部推测请求；浪费 token 占比 | — |

## 2. 现在的触发机制（精确描述）

```
系统音频 ─► WhisperStream(VAD) ─► partial（每 2 s）/ final（静音 0.8 s 后，单段上限 25 s）
麦克风   ─►        同上（阈值更高）                         │
                                                              ▼ SegmentUpdate
VAD 信号：对方语音起始 / 我持续说话(≈1 s) ─────────► TurnDetector（纯逻辑）
                                                              │  .schedule(delay,key) / .cancel
                                                              ▼
                                       AppModel：Task.sleep(delay) ─► fireAuto ─► detector.shouldFire
                                                              ▼
                                  ask(auto:true)：[截图] → 组装提示词 → LLM 流式 → 显示 / “无需回答”则隐藏
```

`TurnDetector` 的决定依据：①需不需要回应（`ResponseCue`）；②句末类型 → 等待时间（问号 0.5 s / 完整句 1.5 s（无线索 +1 s）/ 犹豫 6 s / 无标点 4.5 s，减去已过去的识别耗时）；③取消条件：对方又开口（VAD 与识别结果）、我在说话（文字 ≥6 字且非回声，或持续说话 ≈1 s 且对方已安静）、回声；④同一轮只触发一次，最小间隔 1.5 s。

## 3. 延迟预算

> 对方说完 → 第一个字显示。**“未测”= 没有任何数据**。

| 段 | 现在 | 依据 |
|---|---|---|
| ① VAD 定稿 | 0.8 s（固定） | `Transcriber.swift:244` |
| ② 识别（final） | 0.26 s（2 s 语音）/ 0.42 s（8 s）/ 0.55 s（≥12 s） | [实测] small，Apple 芯片，同机三次重复一致 |
| ②′ 排队 | 0 ~ 0.55 s（前面有 partial 在跑时） | [实测] 请求串行；8 次递增 partial（2→16 s）累计 3.54 s |
| ③ 规则等待 | `max(0.05, wait − 已耗时)`，问号/句号基本 = 0.05 s | `TurnDetector.schedule` |
| ④ 截图（若开启） | **未测** | `AppModel.swift:265` 同步 `await`，在请求之前 |
| ⑤ 组装提示词 + 建连 | **未测**（TLS 首次握手可能 0.1–0.3 s [假设]） | `URLSession.shared` |
| ⑥ LLM 首字（含缓存） | **未测**（取决于服务商/模型/缓存命中） | — |
| ⑦ 渲染 | 可忽略 [假设] | — |
| **①+②+③ 小计** | **≈ 1.2–1.35 s（无排队）/ ≈ 1.8 s（排队最坏）** | [实测推算] |

**含义**：1.55 s 是评测里的保守假设，不是真实值。**在拿到 ④⑤⑥ 的数据之前，不要把“触发延迟 P95 ≤ 1.2 s”当作优化目标**——E2E 里更大的头很可能是 ⑥。

## 4. 问题清单与方案（一个一个解决）

> 每个问题：现象与证据 → 根因 → **推荐方案** → 备选 → 实现要点 → 测试/评测 → 验收 → 风险与人工验证 → 依赖/量级。
> 任务号 `T-2xx` 与 `docs/plan/roadmap-context-timing-ui.md`（PR #3）里的编号一致或为其细化。

### P1　端到端时序遥测（最先做）　`T-204` + `T-101` 的时序部分　量级 M
- **现象**：没有 E2E 数据，所有延迟优化都是猜。
- **推荐方案**：给每一次触发建立一条 **TriggerTrace**（纯数据，在 Core）：记录时间点 `speechEnd`（VAD 判定的说完时刻）→ `vadFinal` → `asrDone` → `ruleWaitEnd` → `fire` → `screenshotDone` → `requestSent` → `firstByte` → `firstToken` → `uiShown`，以及**取消原因码**（对方又开口 / 我在说话 / 回声 / 已回答 / 手动）和决定依据（句末类型、等待时长、是否需要回应）。AppModel 在各环节打点，保存到内存环形缓冲（最近 50 条），可导出 JSON，设置里一个“诊断”开关在界面显示最近一条的分段耗时。
- **备选**：只用 `os_signpost` 打点——开发者可用 Instruments 看，但用户和 DSH 无法直接读，所以不够。
- **实现要点**：新文件 `Core/TriggerTrace.swift`；`TurnDetector.Action` 增加原因码（不改变现有行为）；`ask()` 内打 `screenshotDone/requestSent/firstByte/firstToken`；LLM 流式回调拿到首字节/首 token 时间；**不记录音频、截图，文本只记长度和哈希**。
- **测试/评测**：纯逻辑单测（每条取消/触发路径都有正确原因码）；用 `--selftest-context` 的 mock 服务器验证时间点单调、分段之和 = 总和；评测指标必须**完全不变**。
- **验收**：mock 场景下导出的 trace 能还原每段耗时；真实环境由用户跑一场并把导出文件（已脱敏）贴出来。
- **风险**：打点本身的开销（可忽略）；隐私（只存长度/哈希）。**需要人工**：真实数据。
- **依赖**：无。**这是后面所有延迟任务的前置。**

### P2　自动触发打断上一条正在生成的回答（缺陷）　`T-203`　量级 S–M
- **现象**：`ask()` 一开头就 `askTask?.cancel()`（`AppModel.swift:243`）。自动触发（含最后判定为“（无需回答）”的）会截断你正在看的答案。
- **根因**：取消/替换的策略写在 `ask()` 里，没有区分手动/自动、同一轮/不同轮。
- **推荐方案**：把策略抽成 Core 的纯状态机 `AnswerScheduler`：
  - **手动触发**：取消在途请求并显示新答案（与现在一致）。
  - **自动触发、同一轮的延伸**（对方补充了问题，抢答后又说完）：新请求**先隐藏**，收到前几个字符确认不是“（无需回答）”后，才取消旧的并显示新的。
  - **自动触发、新的一轮**：旧答案**保留**（折叠/下移），新答案隐藏直到确认有实质内容后显示在上面。
  - **“（无需回答）”**：只丢弃新请求，旧答案不受任何影响。
- **备选**：自动触发时只要还有在途请求就不发新请求——最简单，但对方连续追问时会漏。
- **实现要点**：`AnswerScheduler` 输入事件 `requestStarted(id, kind, turnKey)`、`chunk(id, text)`、`finished(id)`；输出命令 `show/hide/cancel(id)`；AppModel 只执行命令。哨兵检测要容忍流式前缀（“（无需”）。
- **测试**：每条规则一个单测 + 一个乱序/并发的随机序列测试（不变量：同一时刻最多一个可见的“当前答案”；旧答案不会被“无需回答”的新请求截断）。
- **验收**：不变量测试通过；评测指标不变；人工验证：连续两个问题、对方补充问题、无需回答三种场景。
- **风险**：两个请求并发时多花的 token（新请求先隐藏的那几百毫秒）；UI 需要“待显示”状态（与 T-302 衔接，先用最小实现）。
- **依赖**：无（UI 展示细节依赖 T-301/T-302，可先做逻辑）。

### P3　截图在触发的关键路径上　`T-209（新）`　量级 S
- **现象**：`ask()` 里同步 `await Screenshot.capture` 之后才组装请求（`AppModel.swift:265`），而截图开关是全局的，所有预设都带；图片 base64 还会增大请求体和模型处理时间。
- **推荐方案（分两步）**：① **先量**（P1 的 `screenshotDone`）。② 若耗时显著：**自动触发预取截图**——对方这一轮开始说话（VAD 起始）时就在后台截一张并保存在内存里，触发时直接用（超过 N 秒的作废）；同时自动触发默认把图缩到 1024 px。逐预设的截图开关（T-307）一起做，**默认只有“屏幕解读”带图**。
- **备选**：自动触发一律不带图（最快，但“屏幕解读”类场景用不了）。
- **测试**：预取缓存的过期/覆盖逻辑单测；截图失败不阻塞触发。
- **验收**：自动触发路径上截图耗时 ≈ 0（命中预取）；人工验证：屏幕解读场景图片是对方提问时刻的屏幕，不是更早的。
- **风险**：预取会在对方每次开口时截图（CPU/隐私：只在内存、不落盘，沿用“不保存截图”的红线）；多显示器选屏逻辑要保持。
- **依赖**：P1（决定是否值得）。

### P4　识别引擎串行，partial 与 final 抢队列　`T-210（新）`　量级 M
- **现象**：`WhisperEngine` 是 actor，两路音频的所有请求串行 [实测：两个 12 s 请求并发总耗时 0.92 s ≈ 2×0.46]。一路 16 s 语音会产生约 8 次递增 partial，累计 3.54 s 引擎时间 [实测]；final 排在 partial 后面会多等最多 ~0.5 s；大模型（turbo）或慢机器上会累积。
- **推荐方案**：给识别请求加**优先级队列**：final > partial；final 到来时丢弃队列里尚未开始的 partial；引擎忙时跳过 partial（下次再识别）；partial 只识别**最近 12 s** 的窗口（成本有上界，实测 ≥12 s 之后耗时不再增长）；**麦克风通道默认不做 partial**（它的 partial 只用于显示，触发已经改用 VAD 信号和 final）。
- **备选**：两个 `WhisperKit` 实例并行——占内存翻倍，Apple 芯片上两个实例仍竞争同一个 ANE，收益不确定。
- **实现要点**：`WhisperEngine` 内部自建带优先级的任务队列（actor 里排序执行）；`WhisperStream.partial()` 增加窗口与忙时跳过；暴露 `queueWait` 指标给 P1。
- **测试/评测**：ASR 评测（final 文本必须与基线逐句一致）；新增负载测试：合成两路各 5 分钟连续语音，记录 final 排队时间 P95（目标：< 0.1 s）；`StreamSignalTests` 不退化。
- **验收**：负载测试下 final 排队 P95 < 0.1 s；ASR 指标不变。
- **风险**：partial 变少会让界面实时显示变“慢”（只影响显示，不影响触发）；窗口化 partial 文本只是后 12 s——显示时要和已定稿部分拼接。**需要人工**：慢机器/大模型下的实际表现。
- **依赖**：P1（先看排队是否真的是问题）。

### P5　推测式定稿：不等满 0.8 s 就开始识别　`T-211（新）`　量级 M–L　**默认关闭的设置开关**
- **现象**：定稿要等静音 0.8 s，再识别 0.3–0.55 s，两段是串行的；这占了触发延迟的绝大部分。
- **推荐方案**：静音达到 **0.4 s**（可配）时就用已有的音频**提前做一次 final 质量的识别**（provisional），同时 VAD 继续等；若 0.8 s 内对方又开口，丢弃这次结果（`onSpeechStart` 已经会取消待触发）；若静音持续到 0.8 s，直接确认——识别结果此时已经就绪。**触发下限从 ≈1.2–1.35 s 降到 ≈0.85 s**。
- **备选**：把 VAD 定稿静音直接缩到 0.6 s——只省 0.2 s，且会把句内短停顿切成多段、Whisper 丢上下文、识别变差。
- **实现要点**：`WhisperStream` 增加 provisional 阶段与 `provisionalAfter` 参数；provisional 结果以“**未定稿但可用于决定**”的更新送给 `TurnDetector`（行仍保持 partial，以免破坏“整场对话只含已定稿句”的前缀稳定性）；确认时转为 final（同一 segment id，文本通常不变）。多出的识别请求要走 P4 的优先级（provisional 与 final 同级）。
- **测试/评测**：ASR 评测不退化；新增时序评测变体（扩展回放里加入 provisional 阶段）量化 T_trigger；单测：provisional 后对方在 0.4–0.8 s 内又开口 → 不触发、文本不泄漏到上下文。
- **验收**：扩展评测 T_trigger P50 ≤ 0.9 s；识别额外负载（每个 ≥0.4 s 的停顿多一次识别）在负载测试里 final 排队 P95 < 0.1 s。
- **风险**：识别负载增加（句内停顿多的人更明显）；provisional 与 final 文本不一致时的抖动。**需要人工**：真实语速和停顿分布（用 P1 的 trace 统计）。
- **依赖**：P1、P4。

### P6　推测式请求：触发之前就发出 LLM 请求　`T-212（新）`　量级 L　**默认关闭的设置开关**
- **现象**：即使触发延迟降到 0.85 s，首字还要再等 LLM（含缓存）若干秒。
- **推荐方案**：在 provisional 阶段、**且判断“大概率说完”（句末问号，或完整句且有提问线索）**时，就**隐藏地**发出 LLM 请求；对方继续说 → 取消；静音确认到 0.8 s → 揭示（显示）。首字延迟被 provisional 到确认之间的 0.4 s 以及建连/缓存预热覆盖。
- **备选**：只做“预热”——触发前先发一个极短请求把连接建好、把整场对话前缀打进缓存。**成本低很多，作为 P6 的第一步先做**。
- **实现要点**：复用 P2 的“隐藏直到确认”机制（`AnswerScheduler` 增加 `speculative` 种类）；限制并发（同一时刻最多 1 个推测请求）；取消要真正中断网络请求（`URLSessionTask.cancel`）。
- **测试/评测**：mock 服务器验证取消/揭示时序；扩展评测统计推测浪费率；成本估算（按 P1 的 token 用量）。
- **验收**：mock 场景下 E2E_first_token 比非推测路径少约 provisional→确认的时间；浪费率 ≤ 20%（句末问号时推测）；默认关闭时行为与现在逐字节一致。
- **风险**：多花钱（每次取消仍计输入 token；有缓存时便宜）；与 P2 的状态机复杂度叠加；**必须真实环境验证**。
- **依赖**：P1、P2、P5；**需要用户决定可接受的额外费用（见 §7）**。

### P7　不以确认词开头的陈述仍误触发　`T-206`　量级 M　**可选**
- **现象**：“我们公司主要做推荐系统。”这类陈述会触发调用（规则法只认确认词/过渡语）。冻结评测误答 25.0%，其中 me_interrupt 占 5/5（属于另一类，由“我在说话”信号处理）。
- **伤害评估**：P2 修好之后，误触发的后果只是**费用**和一次被隐藏的请求，**不再截断答案**。所以优先级低于 P2/P5。
- **推荐方案**：先**度量**（P1 的 trace + 留出集 `T-202`）再决定。若需要做：**可选“语义门”**，仅对“无提问线索且非确认”的歧义轮次，**与主请求并行**发一个极短的判断请求；判断为“无需回答”就丢弃主请求。**默认关闭**。
- **备选**：接受现状，让主模型的“（无需回答）”兜底（现在就是这样）。
- **验收**：留出集上误答 ≤20% 且漏答不退化；关闭时行为不变。
- **依赖**：P2、T-202。

### P8　评测要反映真实流水线　`T-201`、`T-202`、`T-207`　量级 M　**DSH 独立完成**
- **问题**：冻结评测的时序模型假设识别 0.7 s、没有早期信号；扩展评测是我一个人写的假设；规则词表可能过拟合我合成的数据。
- **方案**：①**评测 v2**：由 DSH 独立实现时序模型，纳入 VAD 起始（0.2 s）、“我在说话”（≈1.0 s）、**识别耗时按语音长度取实测值（0.26/0.42/0.55 s）**、引擎排队；v1 保留。②**留出集**：DSH 盲写 ≥40 段新对话（**不读 `ResponseCue`/`Ending` 词表**），测泛化。③**真实环境验证包**：人工验证清单 + 只记事件时间线的采集脚本（**不存音频**），产出可贴进 STATUS 的表。
- **验收**：v2 复现扩展评测数字（±0）；留出集给出泛化差距；验证包覆盖 VAD 误取消、混响尾音、打字噪声、外放回声、提示音。
- **依赖**：Q-002（是否新建 v2）；P1 的 trace 格式（用于验证包）。

### P9　触发模式与用户控制　`T-213（新）`　量级 M　**需要用户决定产品形态**
- **问题**：只有“自动回答开/关”；“灵敏度”现在对问号/句号结尾几乎没有影响（被识别耗时盖住了），用户看不懂；没有“检测到问题但先不显示”的选项；没有区分面试/会议/导师交流。
- **方案**：三种模式——**手动**（只在快捷键/按钮时）、**自动**（默认）、**半自动**（检测到问题后**预生成**，界面显示“检测到：<问题>”，按键（⌃⌥A）才展示——零误答打扰，且首字几乎即时）。“灵敏度”改名为“等待说完的时间”并说明；状态条显示“对方在说话 / 等待说完 / 生成中 / 无需回答”（T-302）。
- **依赖**：P2（隐藏/揭示机制）、T-301/T-302（UI）。

### P10　鲁棒性小项（各自独立，S）　`T-208（新）`
| # | 问题 | 现象/证据 | 方案 | 验收 |
|---|---|---|---|---|
| a | 对方一路有持续背景声（音乐/视频）时 VAD 永远不静音 | 阈值固定 0.008，段上限 25 s 才强制定稿 | 系统通道用自适应噪声底（滑动最小能量 × 系数）作为阈值 | 合成“语音 + 背景音乐”音频上，问题说完后 ≤1.5 s 内定稿；原有评测不变 |
| b | 单段 25 s 上限可能把一个长问题从句中切开 | `Transcriber.swift:250` | 上限处优先在最近的低能量点切；切开后仍按“无标点”等待 | 长题测试不抢答 |
| c | `shouldFire` 要求“没有对方的 partial 行”，若某段 final 丢失（引擎错误/队列积压）会永久阻塞触发 | `TurnDetector.shouldFire` | partial 行加最大存活时间（如 5 s），过期视为已结束 | 注入丢失 final 的单测 |
| d | 重新开始监听时检测器状态不清 | `AppModel.start()` 没有 `detector.reset()` | 开始监听时重置 | 单测 |
| e | 每段语言自动检测可能判错（中英），导致线索词表对不上 | `WhisperEngine.transcribe` | 线索词表同时对两种语言匹配（已是）；记录语言到 trace，统计误判 | trace 中有语言字段 |
| f | 电脑睡眠/唤醒、音频设备切换后流不恢复 | 无处理 | 监听 `captureStopped` 之外再监听设备变更，自动重启 | 人工验证 |

## 5. 实施顺序与依赖

```
              ┌─► P2 打断缺陷 ───────────────┐
```

## 6. 评测与验证策略

- **每个 MR 必须**：`swift build`、`scripts/test.sh`、`EVAL_ASR=0 scripts/eval.sh`、冻结校验通过；**冻结指标不得退化**（有意的取舍要在 MR 里说明）。
- 触发延迟类改动（P4/P5/P6）：除冻结评测外，必须有**扩展回放变体**量化 T_trigger/E2E，并报告负载测试（final 排队）和 ASR 评测不退化。
- **不能自动验证的**（真实麦克风/外放/会议/网络/LLM 延迟）：写进 MR 的“需人工验证”并给出可直接执行的清单，**不得写成“已解决”**。
