### 2.3 缺失的

1. **产品缺陷：自动触发会打断上一条还在生成的回答**（§1 证据）。面试中最糟的体验是：你正在看的答案被一次“其实不需要回答”的触发截断了。→ 新增 **T-203**。
2. **没有任何 UI 任务** → 新增 §5 / T-301~T-308。
3. **没有测量手段**：缓存到底命中没有、首字延迟多少、每次请求多少 token、为什么没触发——现在全靠猜。→ 新增 **T-101（LLM 用量与耗时遥测）** 和 **T-204（触发决策日志）**。
4. 流程缺口（见 §9）：认领对另一个 agent 不可见；MR 文档与 GitHub PR 两套并存；没有自动门禁；`origin/dev` 不存在；T-000 自己的分支基线已过期。

## 3. 目标一：上下文

### 3.1 现状
每次请求 = 系统提示词 + 会议背景 + **整场双方对话**（已定稿、回声已清洗、前缀只增不改）+ **当前这一轮** + 我随后说的 + 此前建议 + 任务 + 截图。前缀稳定率 100%（评测），当前轮标对 98.3%，3000 句下组装 < 1 s。

### 3.2 真正还没解决的问题
1. **没有证据缓存真的命中。** 评测只能证明“前缀一致”，不能证明服务商缓存生效（DeepSeek 要前缀 ≥ 64 token 才进缓存、OpenAI ≥ 1024、Claude 要显式断点；返回字段各不相同）。不测量，“又快又不丢上下文”只是假设。→ **T-101**
2. **上限按字数（15 万）而不是 token，也没有按模型窗口区分**；长会议每次请求都很贵，用户看不到成本。→ **T-102**（依赖 T-101 的数据）
3. **术语/专有名词**：混杂 CER 25.6% 的根因是英文技术词，而用户在“会议背景”里恰恰会写这些词。把它同时作为 Whisper 提示词和 LLM 背景，是成本最低的改进。→ **T-103**
4. **没有长对话数据集和回答质量基线**，C2–C7（问答回合结构化、事实表、问题改写等）无法评估。→ **T-104、T-105**，之后才有 **T-106**
5. 截图全局开关造成不需要的上下文和费用。→ **T-307**

### 3.3 方案与验收
- T-101：解析三种接口的 usage（OpenAI/DeepSeek 的 `prompt_cache_hit_tokens`/`cached_tokens`、Claude 的 `cache_read_input_tokens`），记首字耗时和总耗时，每次请求记录“提示词字数/token、命中率、首字耗时”；先放内存环形缓冲 + 答案卡片小字，再决定是否持久化。**验收**：三种接口各有 mock SSE 的解析单测；真实环境的命中率由用户在“需人工验证”里确认并记入 STATUS。
- **不做**：在没有 T-101/T-105 数据之前，**不要**动上下文结构（不引入摘要、不做检索）。此前的滚动摘要就是没有数据时拍脑袋做的，已经被整场对话取代过一次。

## 4. 目标二：实时时机

### 4.1 现状（冻结评测 → 扩展评测）
抢答 21.7% → 0.0%、漏答 0、误答 25.0% → 10.0%、重复 17 → 0、延迟 P95 1.55 s。**差距来自冻结评测没有建模产品里已有的两个早期信号**。

### 4.2 问题与方案
| 问题 | 方案 | 任务 |
|---|---|---|
| 正式指标看不到早期信号的收益；扩展评测是我一个人写的假设 | **冻结评测 v2**（新目录 `eval/v2`，v1 保留作历史），由 **DSH 独立实现**时序模型，把 VAD 起始（0.2 s）、“我在说话”（1.0 s，实测）纳入；需要 **Q-002 答“是”** | T-201 |
| 规则词表可能过拟合我合成的数据 | DSH 盲写 ≥40 段留出集，测 `ResponseCue`/`Ending` 的泛化；差距大就收敛规则 | T-202 |
| 自动触发打断上一条回答 | 自动触发的新请求**不取消**仍在生成的上一条；新回答确认有实质内容（不是“（无需回答）”）后再替换/并列显示；手动触发保持取消 | T-203 |
| 不知道为什么触发/没触发 | `TurnDetector` 输出决策记录（原因码、等待时长、取消来源：对方又开口/我在说话/回声/已回答），内存环形缓冲，可导出，UI 里能看（调试开关） | T-204 |
| 延迟下限 1.55 s | 见 §4.3 | T-205 |
| 不以确认词开头的陈述仍误触发 | 可选的“语义门”：仅对“无线索且非确认”的歧义轮次，先发一个极短的判断请求；**默认关闭** | T-206 |
| 真实环境没有验证（VAD 信号误取消、混响尾音、打字、回声） | 人工验证清单 + 采集脚本（只记事件时间线，不存音频） | T-207 |

### 4.3 延迟：我对 T3/缩短 VAD 的分析（T-205 先做 spike，不直接实现）
1.55 s = VAD 定稿 0.8 s + 识别 0.7 s（实测识别 P50 只有 0.37 s，所以真实值可能约 1.2–1.3 s，**先用 T-101/T-204 测真实值，再谈优化**）。
- **缩短 VAD 定稿（0.8 → 0.5 s）**：直接降 0.3 s，但会把对方句内的短停顿切成多段，Whisper 丢上下文，识别变差；风险在 ASR，要用 ASR 评测验证。
- **推测式生成（T3）**：在定稿前就用已有的临时结果发起请求，对方继续说就取消。能把延迟藏起来，但每次取消仍计输入 token（前缀缓存能压低成本），而且会放大 §2.3 的“打断”问题——**必须先做 T-203**。
- **建议**：先 T-101/T-204（测量）→ 再决定。若真实首字延迟已经 < 2 s，P95 ≤ 1.2 s 这个目标应下调（见 §8 Q-003）。

## 5. 目标三：页面 UI

### 5.1 现状问题（来自代码与此前截图）
| # | 问题 | 影响 |
|---|---|---|
| U1 | 工具栏一行 14 个控件，最小窗口 920 宽，按钮文字被截断（“立…”） | 主操作不突出，窄窗口难用 |
| U2 | **没有“系统此刻在做什么”的可见状态**：空闲/对方在说/在等对方说完/生成中/判断无需回答/出错 | 自动模式下用户不知道它有没有听到问题，不敢信任 |
| U3 | 答案卡片只显示“自动 · 实时回答”这样的标题，**不显示它识别到的问题原文** | 无法判断答的是不是这一问 |
| U4 | 答案区只渲染行内 Markdown，要点列表、标题按原文显示；没有复制/重答/更短/更详细 | 回答不好读、不好用 |
| U5 | 转写区每次更新都自动滚到底，用户往上翻时会被拽回；没有按说话人区分的样式 | 回看困难 |
| U6 | 没有首次使用引导：权限（屏幕与系统音频/麦克风）、模型下载进度和大小、API 连接测试；错误是行内红字，没有“去系统设置”按钮 | 新用户第一次几乎一定卡住（我们已经遇到过多次） |
| U7 | 没有面试场景的紧凑模式（只显示一张大字答案卡，一键隐藏，可置顶） | 面试时屏幕空间和注意力都紧张 |
| U8 | 快捷键只有一个“手动回答”；开始/停止、新话题、复制答案、隐藏窗口都没有 | 面试中要用鼠标 |
| U9 | 全部界面在一个 513 行文件里，无测试 | 多人并行改 UI 一定冲突 |

### 5.2 设计原则
1. **先让状态可见，再谈美化**（U2/U3 优先于 U1）。
2. **所有 UI 逻辑可测**：把“根据 `AppModel` 状态推导出界面状态”做成纯函数（`AssistantState`），在 Core 或 App 的非 UI 文件里写单测；SwiftUI 视图只负责渲染。
3. 先拆文件再并行（T-301），否则两个 agent 一定在 `Views.swift` 上冲突。
4. UI 改动无法自动验收：每个 UI MR 必须附**截图**和**人工验证清单**（由用户或有屏幕录制权限的环境截取），不得声称“已验证”。

## 9. 对 COLLAB 流程的修订建议

1. **认领锁共享**：认领信息在 git 里（board.md）、而 agent 又不能提交 `dev`，另一个 agent 看不到。改为在**所有工作树共享的位置**放锁：`$(git rev-parse --git-common-dir)/collab/locks/T-xxx.lock`（内容：owner、分支、文件范围、时间）；`scripts/collab-status.sh` 读取并显示。
2. **MR 只用一套**：以 **GitHub PR** 为准（你在 GitHub 上审核），`collab/mrs/` 的模板内容并入 `.github/pull_request_template.md`；`board.md` 只保留任务状态。
